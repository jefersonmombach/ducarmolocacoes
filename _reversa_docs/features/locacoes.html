Ciclo de Vida das Locações

Operação Core

Orquestra o ciclo completo de locação de trajes para eventos comemorativos: seleção de cliente, produtos locados, datas de contratação, evento, entrega e devolução, controle financeiro (total, sinal de 20%, adiantamento, saldo) e máquina de estados (`EnumSituacaoLocacao`).

Requisitos Funcionais Especificados 5 Requisitos
ID Requisito Prioridade Critério de Aceite
RF-LOC-01 Criar locação com itens Must POST `/api/locacaos` persiste a locação e a lista de `LocacaoProduto` associados.
RF-LOC-02 Emissão automática de contrato Must Ao atualizar com `situacao = 1`, o backend gera `htmlContrato` preenchido.
RF-LOC-03 Registro de entrega e devolução Must Ao mudar para situação 2 ou 3, preenche `dataEntrReal` ou `dataDevReal` automaticamente.
RF-LOC-04 Verificação de conflito de agenda Must `listLocacoesProdutoByDataEvento` retorna locações conflitantes no intervalo `[dataEvento-3, dataEvento+4]`.
RF-LOC-05 Atualização parcial (Patch) Should Endpoint de patch permite atualizar campos específicos via reflexão.
Regras de Negócio & Invariantes
  • Sinal Obrigatório (RN-01):** O valor do sinal (`valorSinal`) deve corresponder contratualmente a no mínimo 20% do valor total da locação para efetivar a reserva. 🟢
  • Saldo Devedor na Retirada (RN-04):** O locatário deve quitar o saldo devedor (`valorSaldo = valorTotal - valorSinal - valorAdiantado`) até a data prevista de entrega dos trajes (`dataEntrPrev`, liberado após as 16h). 🟢
  • Recálculo Mandatório do Saldo no Backend (RN-09):** O backend recalcula e sobrescreve forçosamente `valorSaldo = valorTotal.subtract(valorSinal).subtract(valorAdiantado)` no método `save()`, blindando a persistência contra adulterações ou arredondamentos incorretos do cliente. 🟢 [Validado com o usuário]
  • Preenchimento de Timestamp Real:** A transição para situação 2 preenche `dataEntrReal = now()`; a transição para situação 3 preenche `dataDevReal = now()`. 🟢
  • Janela de Proteção de Trajes com Bloqueio Impeditivo (RN-08):** Para evitar dupla locação, o traje não pode estar reservado em outra locação entre 3 dias antes e 4 dias depois da data do evento. Caso haja colisão, o backend aborta o salvamento lançando erro 400 (Bad Request). 🟢 [Validado com o usuário]
Critérios de Aceitação Formal (Gherkin)
Cenário: Emissão do contrato de locação
  Dado que uma locação está no estado 0 (NOVO)
  Quando o operador altera o status para 1 (CONTRATO_EMITIDO)
  Então o sistema deve invocar o TagProcessor
  E o campo htmlContrato deve conter a minuta HTML com nome, CPF, datas e trajes preenchidos

Cenário: Retirada dos trajes pelo cliente
  Dado que a locação está no estado 1 (CONTRATO_EMITIDO) com saldo devedor quitado
  Quando o operador altera o status para 2 (TRAJES_ENTREGUES)
  Então o sistema deve preencher automaticamente dataEntrReal com a data e hora atuais
